# 03 - Authentication & Authorization

This document covers how the ESM legacy Rails 4.2 EMR platform authenticates users and authorizes access to operations. It is written for the engineer taking full ownership and is deliberately blunt about the security posture: the auth subsystem is bespoke, weak, and in several places broken or dead. Every claim below is grounded in source with `file:line` citations.

For how requests reach the authorization gate, see **02 - Request Flow & Routing**; for the dynamic class generation that runs *after* authorization, see **05 - Metadata-Driven Architecture** and **07 - Operation Execution Flow**.

> Scope note on SSO: `saml2`, `omniauth`, and `omniauth-google-oauth2` are declared in the `Gemfile` (`Gemfile:17,113-114`) but a full-repo grep finds **zero** references to SAML2/OmniAuth/`provider` anywhere in `app/lib/config/views`. **SAML2 and Google OAuth login are not implemented.** Treat any documentation or stakeholder claim of SSO/Google login as unverified and, on the current evidence, false. The only working login path is the home-grown username/password flow described below.

## 1. Overview

| Concern | Implementation | Where |
| --- | --- | --- |

| Credential check | `User.authenticate` (active users only) | `app/models/user.rb:36-45` |
| SSO (SAML/Google) | **Declared in Gemfile, never wired — non-functional** | `Gemfile:17,113-114` |

| Session secret | Hard-coded, committed; `secret_token == secret_key_base` | `config/initializers/secret_token.rb:7-8` |
| `current_user` (per request) | Re-loaded in `EsmController#context_filter` | `app/controllers/esm_controller.rb:53-65` |

| RBAC enforcement | **`Permission` table exists but is never consulted** | `app/models/permission.rb` |
| API auth | `params[:user_id]` + `params[:api_key]` == `hashed_password` | `app/controllers/esm_proxy_controller.rb:57-62` |
| CSRF on dynamic surface | **Disabled** (`skip_before_filter :verify_authenticity_token`) | `app/controllers/esm_proxy_controller.rb:4` |

There is **no Devise, no `bcrypt`, no `has_secure_password`**. Authentication and authorization are two separate, hand-rolled mechanisms. The platform uses Rails 4 legacy `protected_attributes` (`attr_accessible`/`attr_protected`) instead of strong parameters.

## 2. Login flows

### 2.1 Password login (the only real flow)

Login is handled by `UserController#login`. Two credential sources exist: a per-solution MongoDB user model and the global MySQL `users` table.

1. Browser POSTs `/user/login` with `params[:user][:login]` and `params[:user][:password]` (and optionally `:esm` and `:remember`).
2. If a solution (`params[:user][:esm]`) is provided, the controller first tries the per-solution Mongo user model, comparing `User.encrypt(pass, salt)` against the stored hash.
3. Otherwise it falls through to `User.authenticate(login, password)` (`app/models/user.rb:36-45`), which loads the *active* user (`activate is null or activate != 0`) and compares `SHA1(pass + salt)` to `hashed_password`.
4. On success: `session[:user] = @user.id` (`app/controllers/user_controller.rb:113`). If `params[:remember]` is set, a remember-me cookie is written.
5. Redirect to `session[:return_to]`, else a project home, else solution home, else `/`.

```ruby
# app/models/user.rb:36-45
def self.authenticate(login, pass)
  u = self.where("login = ? and (activate is null or activate != 0  )", login).first()
  return nil if u.nil?
  if User.encrypt(pass, u.salt) == u.hashed_password
    u.last_accessed = Time.now
    u.save
    return u
  end
  nil
end
```

```ruby
# app/models/user.rb:131-133
def self.encrypt(pass, salt)
  Digest::SHA1.hexdigest(pass+salt)
end
```

The salt is a 10-char alphanumeric string generated by `User.random_string` using **Ruby `Kernel#rand`, not a CSPRNG** (`app/models/user.rb:62-66,157-163`) — predictable, low-entropy salts.

#### Remember-me cookie stores the password hash as a bearer token

When "remember" is checked, the controller stores the raw `hashed_password` in `cookies[:login]` with a 7-day expiry (`app/controllers/user_controller.rb:104-111`):

```ruby
# app/controllers/user_controller.rb:104-110
if params[:remember]
  unless params[:user][:esm]
    cookies[:login] = { :value => @user.hashed_password, :expires => Time.now + 3600*24*7}
  else
    cookies[:login] = { :value => @user.hashed_password, :expires => Time.now + 3600*24*7}
    cookies[:esm]   = { :value => esm.name, :expires => Time.now + 3600*24*7}
  end
end
```

On a later visit, the login path treats a matching `hashed_password` cookie as proof of identity (`app/controllers/user_controller.rb:90-95` resolves the per-solution user by `where(:hashed_password => cookies[:login])`). **The stored password hash is effectively a permanent bearer credential** — capturing it (or the at-rest value) grants login.

### 2.2 SAML2 / Google OAuth — unwired

The gems are bundled but no initializer, no `provider` block, no controller/route/view references exist. The Dockerfile even installs `libxmlsec1` (a SAML dependency), which hints at intent, but there is no wiring in the codebase. **Do not assume any external IdP is involved.** This is an open finding only in the sense of "could a non-committed deploy-time initializer wire it?" — no such file exists in `config/initializers`, so the honest answer is: as shipped, SSO does not work.

### 2.3 Forgot password

`User#send_new_password` generates a new random password and emails it **in cleartext** via the Rails 2-style API `Notifications.deliver_forgot_password(...)` (`app/models/user.rb:68-73`).

> **Unverified / to confirm:** the `Notifications` mailer class and whether the Rails-2 `deliver_*` API still functions under Rails 4.2 were not located/traced in the auth reading. Treat password-reset email delivery as unverified until tested.

## 3. Sessions and `current_user`

### 3.1 Session storage

Sessions use Rails `CookieStore` (client-side) with key `_esmx_session` (`config/initializers/session_store.rb:3`). Only the integer user id is stored in `session[:user]`. The signing secret is committed to the repo, and `secret_token` and `secret_key_base` are **identical** (`config/initializers/secret_token.rb:7-8`).

> Because the session is client-side and the signing key is known to anyone with repo access, **session cookies can be forged**. Combined with the role logic in §4, this is a privilege-escalation primitive. No `secure`/`httponly` flags are configured and `force_ssl` is commented out in `production.rb` (see **06 - Docker & Infrastructure / Deployment**).

### 3.2 `current_user` is resolved twice, two different ways

There are two parallel implementations, which is a frequent source of confusion:

- **Legacy `BasicAuth#current_user`** simply returns `session[:user]` — i.e. the *id*, not a `User` object (`lib/basic_auth.rb:62-64`). `BasicAuth` is mixed into `EsmController` (`app/controllers/esm_controller.rb:1-3`).
- **`EsmController#context_filter`** (the real per-request bootstrap, a `before_filter` on every ESM controller — `app/controllers/esm_controller.rb:8`) loads the actual object and sets `@current_user`, `@current_solution`, and `@current_role`.

`context_filter` branches on the *string length* of `session[:user]`:

```ruby
# app/controllers/esm_controller.rb:53-65
if session[:user]
  if session[:user].to_s.size < 10
    @current_user = User.find(session[:user])
    ...
    @current_role = Role.new(:name=>'user').name           # => the STRING 'user'
    @current_role = 'developer' if @current_solution and @current_solution.user == @current_user
  elsif session[:esm]
    @current_solution = Esm.find session[:esm]
    @current_user, @current_role, @solution_user = @current_solution.get_user_role_by_id session[:user].to_s
    ...
  end
end
```

Key facts to internalize:

- An id **< 10 chars** is treated as a MySQL `User` row id; `@current_role` is set to the **String** `'user'` (or `'developer'` if the user owns the solution).
- An id **>= 10 chars** with `session[:esm]` present routes through `Esm#get_user_role_by_id` (`app/models/esm.rb:61-82`), which loads a per-solution Mongo user wrapped by `User.mock_user`.

> **Unverified / to confirm:** the `>= 10`-char branch (`Esm#get_user_role_by_id` → `www.get_user_by_id` → Mongo user model) and its password-verification semantics were not fully traced in the auth reading. If you touch login for per-solution (Mongo-backed) users, trace this path before changing anything.

### 3.3 Solution selection is client-influenceable

Both `context_filter` and `BasicAuth#login_required` resolve the active solution from `Esm.find_by_url(request.host)`, then `cookies[:esm]`, then the URL subdomain (`app/controllers/esm_controller.rb:15-28`, `lib/basic_auth.rb:25-38`). Tenant selection therefore trusts the host header and a client cookie. Cross-reference **02 - Request Flow & Routing** for how this interacts with multi-tenant dispatch.

## 4. Authorization: the string ACL system

There is **no RBAC enforcement**. Authorization is a flat, string-based ACL keyed off space-separated tokens on the `acl` column of `Service`, `Operation`, `Project`, and `MenuAction` (added by `db/migrate/20120612075609_add_acl_to_esm_projects.rb`).

### 4.1 ACL tokens

| Token | Meaning |
| --- | --- |
| `*` | Public / everyone |
| `user` | Any logged-in user |
| (blank) | Owner-only |
| `<role-name>` | Users whose `@current_role` matches that name |

### 4.2 The authorization gate (`EsmProxyController#index`)

The real decision happens in the dynamic dispatcher. After resolving the `Service`, the controller computes the inherited ACL and checks membership before invoking the operation:

```ruby
# app/controllers/esm_proxy_controller.rb:57-80
if @current_user
elsif params[:user_id]
  @current_user = User.where(:id=>params[:user_id], :hashed_password => params[:api_key]).first
end

acl = s.get_acl params[:opt], @current_user
acl << 'user' if acl.size == 0                              # default-opens to any logged-in user

if  acl.index('*')!=nil or (@current_user and (@context.user == @current_user or acl.index 'user' or (@current_role!=nil and acl.index( @current_role)) ))
  @project_instance = @current_project.get_instance
  context = s.prepare(params,self,request)
  obj = s.load context
  out = obj.send params[:opt], params                       # <-- operation dispatched here
else
  session[:return_to]=request.fullpath
  render :text=>'<br/>...You are not authorized to use this service!!...'
end
```

Access is granted if **any** of:

1. ACL contains `*` (public); or
2. there is a `@current_user` **and** one of:
   - the user is the solution owner (`@context.user == @current_user`), or
   - ACL contains `user`, or
   - `@current_role` is non-nil and matches an ACL token.

Cross-reference **07 - Operation Execution Flow**: once authorized, `obj.send(params[:opt], params)` invokes a method on a class that was `eval`'d from DB-stored metadata — authorization is the only gate before that runs.

### 4.3 ACL inheritance (`Service#get_acl`)

`Service#get_acl` walks the service inheritance chain (`s = Service.find_by_package s.extended`), merging service-level and operation-level `acl` tokens (`app/models/service.rb:333-366`). Inheritance is via the `extended` package-string column (added by `db/migrate/20120518152807_add_project_inheritance_to_esm_projects.rb`).

> **Cyclic/recursive risk:** `Service#get_extended` calls itself unconditionally and would stack-overflow if invoked (`app/models/service.rb:46`); `get_acl`'s `find_by_package` loop can also loop on cyclic `extended` references. See **05 - Metadata-Driven Architecture**.

### 4.4 API-key authentication

When no `@current_user` is established, the dispatcher authenticates by query/body params: `User.where(:id => params[:user_id], :hashed_password => params[:api_key]).first` (`app/controllers/esm_proxy_controller.rb:60`). **The API key *is* the stored password hash**, transmitted in the URL/body — so the same value is both the at-rest secret and the wire credential, and it will land in access logs and proxies.

### 4.5 The `/ws/` bypass

There is a second dispatch path, `EsmProxyController#ws`, mapped from `ws/:service/:opt` (`config/routes.rb:61`). It loads the service and calls `obj.send(params[:opt], params)` with **no ACL/authorization check at all** (`app/controllers/esm_proxy_controller.rb:195-217`). Any operation reachable via `/ws/` is effectively public. See **02 - Request Flow & Routing**.

### 4.6 Admin scaffold gate (`EsmAdminController`)

The auth-table CRUD UIs (`UsersController`, `RolesController`, `PermissionsController`, `AccountsController`) are gated by `EsmAdminController#login_admin_required`, which **only checks that `@current_user` is present** and redirects to `/user/login` otherwise. The intended secondary admin check on line 12 uses `=` (assignment) instead of `==` (comparison): `@current_user.role=nil` always nils the in-memory role, so the branch is **dead/inert** (`app/controllers/esm_admin_controller.rb:6-16`). In effect, *any* logged-in user passes the admin gate.

### 4.7 Per-solution developer access (`Account`)

`Esm#developer?(user)` grants developer rights if the user owns the solution or `user.role.name == 'admin'`, otherwise it searches the solution's `developer`-named `Role`s for an `Account` join with a matching `user_id` (`app/models/esm.rb:133-145`). `Account(esm_id, role_id, user_id, expired_at, active)` is the per-solution role grant, also used by `User#my_solutions` (`app/models/user.rb:111-118`).

## 5. The auth data model

```
MySQL                                  ACL columns (space-separated string tokens)
-----                                  ------------------------------------------
users(login,hashed_password,salt,        esm_projects.acl
      role_id,esm_id) --belongs_to-->     esm_services.acl   --get_acl inheritance-->
roles(name,project_id,esm_id)             esm_operations.acl     via 'extended'

         active,expired_at)  [join: per-solution role grant]

```

| Model / table | Role in auth | Source |
| --- | --- | --- |
| `User` / `users` | Credentials (`login`, `hashed_password`, `salt`, `role_id`, `esm_id`); SHA-1 hashing, role/solution helpers | `app/models/user.rb` |
| `Role` / `roles` | `belongs_to :project`, `has_many :accounts`; only behavior is `developer?` (`name=='developer'`) | `app/models/role.rb` |
| `Permission` / `permissions` | **Dead for auth** — never queried in any decision; only CRUD-managed | `app/models/permission.rb` |
| `Account` / `accounts` | User↔Esm↔Role join granting per-solution developer access | `app/models/account.rb` |
| `Esm` | `get_user_role_by_id`, `developer?` account-based access | `app/models/esm.rb` |

Note the `Permission` model has a full scaffold UI but is never consulted — the "RBAC" surface is misleading. Authorization is purely the string-ACL system. See **04 - Database Structure** and **05 - Core Domain Models** for the wider schema.

## 8. Gotchas / risks

These are the things that will bite you. Ranked roughly by severity.

### Critical

- **Forgeable sessions.** `secret_token`/`secret_key_base` are hard-coded, identical, and committed (`config/initializers/secret_token.rb:7-8`). With `CookieStore`, anyone holding the repo can sign a cookie that sets `session[:user]` to any id — full session forgery / privilege escalation. Rotating this secret is the single highest-value hardening step, but note it will invalidate all existing sessions and remember-me cookies.
- **Weak password storage.** `SHA1(pass + salt)` with no key stretching/work factor (`app/models/user.rb:131-133`); salts from non-CSPRNG `Kernel#rand` (`app/models/user.rb:157-163`). Fast to brute-force.
- **CSRF disabled on the entire dynamic surface.** `skip_before_filter :verify_authenticity_token` on `EsmProxyController` (`app/controllers/esm_proxy_controller.rb:4`) means every state-changing operation accepts cross-site POST/PUT/DELETE.
- **`/ws/` has zero authorization.** `EsmProxyController#ws` dispatches operations with no ACL check (`app/controllers/esm_proxy_controller.rb:195-217`).

### High

- **Password hash doubles as bearer credential.** Remember-me stores `hashed_password` in a cookie and treats it as proof of identity (`app/controllers/user_controller.rb:90-95,104-110`); API auth passes the same hash as `api_key` in the URL/query (`app/controllers/esm_proxy_controller.rb:60`). The hash leaks into logs/proxies and never expires server-side.
- **Default-open ACL.** Empty ACL is coerced to `['user']` (`app/controllers/esm_proxy_controller.rb:66`), so any operation with no ACL configured is reachable by *any* logged-in user.
- **Admin gate is effectively just "logged in".** `EsmAdminController` only verifies `@current_user` presence; the secondary role check is a no-op assignment bug (`app/controllers/esm_admin_controller.rb:6-16`). Any authenticated user reaches the Users/Roles/Permissions/Accounts CRUD UIs.
- **Mass-assignment of credentials.** `User` `attr_accessible` whitelists `:hashed_password` and `:salt` (`app/models/user.rb:5`), so a raw `params[:user]` reaching `new`/`update_attributes` can overwrite credentials directly. (`attr_protected :id, :salt` on line 32 conflicts with the `attr_accessible` whitelist — confirm effective behavior before relying on either.)

### Medium / correctness

- **`@current_role` typing is inconsistent.** It is a **String** in `context_filter` (`app/controllers/esm_controller.rb:63,65`) but a **`Role` object** in `EsmProxyController#access` (`app/controllers/esm_proxy_controller.rb:143-145`). The `#index` path compares `acl.index(@current_role)` (string) while `#access` compares against `@current_role.name`. Fragile; do not assume `@current_role` is one type.
- **Operator-precedence bug in ACL checks.** `role and acl.index '*' or acl.index(role.name)` (`app/models/operation.rb:79`, `app/models/service.rb:380`) parses as `(role && acl.index('*')) || acl.index(role.name)` — the `role.name` branch evaluates even without a role, and `*` matches only when a role is present. Likely not the intended logic.
- **Type/case mismatches that silently never fire.** `User#developer_of_project` compares `self.role == 'Admin'` (a `Role` object vs a String — always false) while `User#developer?` checks `role.name == 'admin'` (lowercase) (`app/models/user.rb:51-60,127-129`). Role checks that look like they grant admin may quietly do nothing.
- **`User#allow?`** returns `acl.index(role)` (a numeric index or nil) used in truthy contexts, and returns true unconditionally for `role == 'developer'` or an empty ACL (`app/models/user.rb:139-150`).
- **No lockout, no rate limiting, no password complexity** beyond a `5..40` length validation. `forgot_password` emails a new password in cleartext (`app/models/user.rb:68-73`).
- **`Permission` is a decoy.** It has a model and scaffold UI but is never queried for any authorization decision (`app/models/permission.rb`). Do not extend it expecting it to take effect.

### Unverified / to confirm

- Whether `Notifications.deliver_forgot_password` (Rails 2 mailer API) still functions under Rails 4.2 (`app/models/user.rb:72`).
- The `>= 10`-char `session[:user]` branch and its Mongo user-model password verification (`app/controllers/esm_controller.rb:67-74`, `app/models/esm.rb:61-82`).
- Whether any non-committed deploy-time initializer wires OmniAuth/SAML — none exists in `config/initializers`, so on current evidence SSO is absent.
- How/when `EsmProxyController#access` is reached vs `#index` (both map to `esm_proxy`), and which governs production traffic — `#access` sets `@current_role = Role.new(:name=>'member')` for cross-solution users (`app/controllers/esm_proxy_controller.rb:144-146`).

> Cross-references: the **eval-based operation execution** that runs after the ACL check is documented in **07 - Operation Execution Flow** and **05 - Metadata-Driven Architecture**; routing/dispatch precedence (including the `/ws/` and catch-all routes) is in **02 - Request Flow & Routing**; the committed-secrets and development-mode-in-production deployment posture is in **06 - Docker & Infrastructure / Deployment**.
